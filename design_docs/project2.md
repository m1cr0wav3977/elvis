# Project 2 Design

## Scope

Project 2 adds an authenticated order API to manager and worker nodes. Each
node accepts structured orders into its own queue and exposes its active
orders. A background processor checks the queue every 60 seconds, logs what
each order would do, and marks it complete without executing commands or
sending HTTP requests.

The supported order kinds are `execute` (a descriptive system-command request)
and `http_request` (a descriptive HTTP-request specification).

## Order model

Each order contains:

- `order_id`: unique identifier within the receiving node; generated by the
  receiver when omitted from a request.
- `origin_node_id`: ID of the node that originated the order.
- `kind`: either `execute` or `http_request`.
- `payload`: a kind-specific object describing the work.
- `created_at`: UTC creation timestamp generated by the receiving node.
- `status`: local lifecycle state, initially `pending`.

For `execute`, `payload.command` is a non-empty command name and
`payload.arguments` is an optional list of strings. For `http_request`,
`payload.method` is one of `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, or
`OPTIONS`; `payload.url` must be an absolute HTTP(S) URL. Optional `headers`
are string-to-string pairs and an optional `body` can contain JSON data.
Unknown envelope and payload fields are rejected.

Example system-command description:

```json
{
  "origin_node_id": "manager-1",
  "kind": "execute",
  "payload": {
    "command": "echo",
    "arguments": ["hello"]
  }
}
```

Example HTTP-request description:

```json
{
  "origin_node_id": "manager-1",
  "kind": "http_request",
  "payload": {
    "method": "GET",
    "url": "https://example.invalid/health",
    "headers": {
      "Accept": "application/json"
    }
  }
}
```

In both cases these are data descriptions only: the current implementation
does not execute the command or send the HTTP request. The optional top-level
`order_id` may be included by the sender; `created_at` and `status` are
receiver-managed and are not accepted as request fields.

## Receiving orders and authentication

The shared order API is exposed by every manager and worker through the common
`Node`. `POST /orders` accepts and validates an order. Authenticated
`GET /orders` lists only the responding node's pending and processing orders;
completed orders are not returned. Each item includes `order_id`,
`origin_node_id`, `kind`, `payload`, `created_at`, and `status`. The response
is `{"orders":[]}` when there are no active orders. The GET endpoint requires
the same configured bearer token as order submission.

Both endpoints require an `Authorization: Bearer <shared-secret>` header.
Each receiving node reads the shared token from its `[auth]` config section:
```ini
[auth]
order_token = <shared-secret>
```

An empty or missing configured token disables order submission and listing;
the respective routes return HTTP `503`. An invalid token is rejected with
HTTP `401`, and the token comparison uses Python's standard-library
`hmac.compare_digest`. After authentication, the route validates the envelope
and kind-specific payload, creates an `Order`, and enqueues it. A successful
request returns HTTP `202` with the order ID and `pending` status. Reusing an
order ID already known to that node is rejected.

The bearer token is a shared secret, not a distinct identity for each peer;
this version does not enforce manager-versus-worker permissions. The API uses
the project's existing Flask HTTP service and does not add an external
dependency. The token is not itself encrypted in transit: use only in the
isolated development setup until transport security is designed and deployed.

## Per-node queue and dry-run processing

Each node owns an `OrderQueue` with a FIFO collection of pending orders and a
lookup of orders already accepted by that node. Taking an order removes it
from the pending FIFO but retains its record for status inspection. Local
status transitions are:

```text
pending -> processing -> completed
```

`main()` starts one background thread per node process. The thread waits 60
seconds after startup, then calls `Node.process_pending_orders()` once per
minute. That method atomically claims the currently pending orders, logs each
order ID, kind, and origin to stdout, updates the existing received/completed
counters, and marks each order complete. Orders received during a processing
cycle are handled in the next cycle. The timer is local to each node; there is
no central scheduler. Processing is synchronous and dry-run only; the
application does not execute a command or send an HTTP request.

## Automated tests

From the source checkout, with `pytest` installed, run the regression suite:

```bash
PYTHONPATH=src python3 -m pytest -q
```

It covers both node types, API authentication and validation, order queues, and
the dry-run processing cycle. The following smoke test checks the deployed
server independently.

## Test the deployed network

The instructor's Linux server runs one manager and two workers. Each node
listens on its own port:

| Config | Role | Port |
|---|---|---:|
| `node1.ini` | Manager | 8081 |
| `node2.ini` | Worker | 8082 |
| `node3.ini` | Worker | 8083 |

All nodes use the same shared order token in their `[auth]` section:

```ini
[auth]
order_token = <shared-lab-token>
```

The API uses unencrypted HTTP and is intended only for the authorized course
server and lab.

Run these checks from a shell on the server, replacing the token placeholder
with the configured value. The status endpoints report each node's role and
its partial peer view; order queues are local to each node.

```bash
for PORT in 8081 8082 8083; do
  curl -i "http://localhost:$PORT/health"
  curl -i "http://localhost:$PORT/status"
  curl -i -H 'Authorization: Bearer <shared-lab-token>' \
    "http://localhost:$PORT/orders"
done
```

Submit one dry-run order to the manager and one to a worker:

```bash
curl -i -X POST http://localhost:8081/orders \
  -H 'Authorization: Bearer <shared-lab-token>' \
  -H 'Content-Type: application/json' \
  -d '{"origin_node_id":"grader","kind":"execute","payload":{"command":"echo","arguments":["hello"]}}'

curl -i -X POST http://localhost:8082/orders \
  -H 'Authorization: Bearer <shared-lab-token>' \
  -H 'Content-Type: application/json' \
  -d '{"origin_node_id":"grader","kind":"http_request","payload":{"method":"GET","url":"https://example.invalid/health"}}'
```

Each accepted request returns HTTP `202` with an order ID and `pending`
status. These payloads are descriptions only: commands are not executed and
HTTP requests are not sent. Nodes process their local queues once per minute,
so an accepted order may complete and disappear from `GET /orders` before it
is queried.

## Updated Architecture

```
                         +----------------+
                         |    Herder      |
                         | (human / CLI)  |
                         +--------+-------+
                                  |
                                  | HTTP API
                                  v
   +--------------------------------------------------------------+
   | Manager (extends Node)                                       |
   | GET /health, /info, /status                                  |
   | Authenticated GET/POST /orders                               |
   |                                                              |
   | Local OrderQueue (FIFO) --> 60-second dry-run processor      |
   | managers[]: partial peer-manager list                         |
   | workers[]: workers overseen by this manager                   |
   +---------------------+----------------------+-----------------+
                         |                      |
              knows of (partial peer)       oversees
                         v                      v
              +-------------------+   +---------------------------+
              | Peer Manager      |   | Worker (extends Node)     |
              | Node              |   | GET /health, /info        |
              | Its own workers   |   | GET /status               |
              | are not visible   |   | Authenticated GET/POST    |
              +-------------------+   | /orders                   |
                                      | Local OrderQueue (FIFO)   |
                                      | 60s dry-run processor     |
                                      | manager_ip: manager's IP  |
                                      +---------------------------+

   Shared Node base: health/info and order routes, identity, and counters.
   /orders endpoints require the shared bearer token.
   Each node owns its queue; orders are not forwarded between nodes.
```

Orders move locally from pending to processing to completed. The periodic
processor logs the order description but does not execute commands or send
HTTP requests. A manager's peer lists describe its partial view; in this
increment, they do not implement order forwarding or inter-node communication.
