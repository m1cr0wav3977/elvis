# Project 2 Design

## Scope

Project 2 adds the first step in node-to-node communication: a node can accept
a structured order, authenticate the sender with a shared bearer token, and
place the order in its local queue. An authenticated caller can also inspect
the node's active orders. Each node drains its own queue in dry-run mode every
60 seconds.

Nodes receive and process orders. There are two types of orders, `execute` and 
`http_request`.

Order processing is intentionally non-operational at this stage. An
`execute` order is not run as a system command, and an `http_request` order is
not sent over the network. Processing logs what would have happened, then marks
the order complete. This provides an end-to-end data and queue lifecycle
without carrying out the requested work.

## Order model

Each order contains:

- `order_id`: unique order identifier; generated by the receiver when omitted
  from a request.
- `origin_node_id`: ID of the node that originated the order.
- `kind`: either `execute` or `http_request`.
- `payload`: a kind-specific object describing the work.
- `created_at`: UTC creation timestamp generated by the receiving node.
- `status`: local lifecycle state, initially `pending`.

For `execute`, `payload.command` is a non-empty command name and
`payload.arguments` is an optional list of strings. For `http_request`,
`payload.method` is one of `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, or
`OPTIONS`; `payload.url` must be an absolute HTTP(S) URL. Optional `headers`
are string-to-string pairs and an optional `body` can contain JSON data.
Unknown envelope and payload fields are rejected.

Example system-command description:

```json
{
  "origin_node_id": "manager-1",
  "kind": "execute",
  "payload": {
    "command": "echo",
    "arguments": ["hello"]
  }
}
```

Example HTTP-request description:

```json
{
  "origin_node_id": "manager-1",
  "kind": "http_request",
  "payload": {
    "method": "GET",
    "url": "https://example.invalid/health",
    "headers": {
      "Accept": "application/json"
    }
  }
}
```

In both cases these are data descriptions only: the current implementation
does not execute the command or send the HTTP request. The optional top-level
`order_id` may be included by the sender; `created_at` and `status` are
receiver-managed and are not accepted as request fields.

## Receiving orders and authentication

The shared order API is exposed by every manager and worker through the common
`Node`. `POST /orders` accepts and validates an order. Authenticated
`GET /orders` lists only the responding node's pending and processing orders;
completed orders are not returned. Each item includes `order_id`,
`origin_node_id`, `kind`, `payload`, `created_at`, and `status`. The response
is `{"orders":[]}` when there are no active orders. The GET endpoint requires
the same configured bearer token as order submission.

The base `Node` registers `GET /orders` and `POST /orders`, so both manager and
worker nodes expose the same order API. Requests use the JSON envelope described
above and an `Authorization: Bearer <token>` header. The receiving node reads
the expected shared token from its configuration:

```ini
[auth]
order_token = <shared-secret>
```

An empty or missing configured token disables order submission and listing;
the respective routes return HTTP `503`. An invalid token is rejected with
HTTP `401`, and the token comparison uses Python's standard-library
`hmac.compare_digest`. After authentication, the route validates the envelope
and kind-specific payload, creates an `Order`, and enqueues it. A successful
request returns HTTP `202` with the order ID and `pending` status. Reusing an
order ID already known to that node is rejected.

The bearer token is a shared secret, not a distinct identity for each peer;
this version does not enforce manager-versus-worker permissions. The API uses
the project's existing Flask HTTP service and does not add an external
dependency. The token is not itself encrypted in transit: use only in the
isolated development setup until transport security is designed and deployed.

## Per-node queue and dry-run processing

Each node owns an `OrderQueue` with a FIFO collection of pending orders and a
lookup of orders already accepted by that node. Taking an order removes it
from the pending FIFO but retains its record for status inspection. Local
status transitions are:

```text
pending -> processing -> completed
```

`main()` starts one background thread per node process. The thread waits 60
seconds after startup, then calls `Node.process_pending_orders()` once per
minute. That method atomically claims the currently pending orders, logs each
order ID, kind, and origin to stdout, updates the existing received/completed
counters, and marks each order complete. Orders received during a processing
cycle are handled in the next cycle. The timer is local to each node; there is
no central scheduler. Processing is synchronous and dry-run only; the
application does not execute a command or send an HTTP request.

## How to test manually

There are two supported three-node test setups below. Run the curl commands
on the Linux machine that hosts the nodes and use `localhost` in both setups.
For Docker Compose on a remote server, SSH to that server and run the commands
there.

From the repository root on the Linux server, build the binary and generate a
shared token:

```bash
./scripts/build.sh
TOKEN="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
printf 'Generated lab token: %s\n' "$TOKEN"
```

Copy the three example configs into a private local directory:

```bash
mkdir -m 700 -p "$HOME/project2-lab"
cp configs/node1.ini "$HOME/project2-lab/manager.ini"
cp configs/node2.ini "$HOME/project2-lab/worker1.ini"
cp configs/node3.ini "$HOME/project2-lab/worker2.ini"
chmod 600 "$HOME/project2-lab/"*.ini
```

Edit each copied config. In its existing `[node]` section set
`host = 127.0.0.1` and the port shown below. Add an `[auth]` section with the
same token in all three files:

| Config | Type | Port |
|---|---|---:|
| `manager.ini` | manager | 8081 |
| `worker1.ini` | worker | 8082 |
| `worker2.ini` | worker | 8083 |

```ini
[auth]
order_token = PASTE_THE_GENERATED_VALUE_HERE
```

Paste the value printed as `Generated lab token` without quotes. Do not edit
the tracked configs or commit these local copies. Start the three binaries in
the background:

```bash
nohup ./build/elvis-node --config "$HOME/project2-lab/manager.ini" \
  > "$HOME/project2-lab/manager.log" 2>&1 &
echo $! > "$HOME/project2-lab/manager.pid"
nohup ./build/elvis-node --config "$HOME/project2-lab/worker1.ini" \
  > "$HOME/project2-lab/worker1.log" 2>&1 &
echo $! > "$HOME/project2-lab/worker1.pid"
nohup ./build/elvis-node --config "$HOME/project2-lab/worker2.ini" \
  > "$HOME/project2-lab/worker2.log" 2>&1 &
echo $! > "$HOME/project2-lab/worker2.pid"
```

In the shell used for the curl commands, set `TOKEN` to the same generated
value:

```bash
TOKEN='PASTE_THE_GENERATED_VALUE_HERE'
```

### Exercise the API on either setup

These commands are identical in both setups. Check health and read each node's
active order queue:

```bash
for PORT in 8081 8082 8083; do
  curl -i "http://localhost:$PORT/health"
  curl -i -H "Authorization: Bearer $TOKEN" \
    "http://localhost:$PORT/orders"
done
```

Health returns HTTP `200`. Authenticated `GET /orders` returns HTTP `200` and
`{"orders":[]}` on a fresh node. The GET requires the bearer token: omitting
it or using a wrong one returns HTTP `401`. If a node has no configured token,
it returns HTTP `503`.

Submit an `execute` order to the manager and an `http_request` order to a
worker:

```bash
curl -i -X POST http://localhost:8081/orders \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"origin_node_id":"manual-tester","order_id":"manual-manager-001","kind":"execute","payload":{"command":"echo","arguments":["hello"]}}'

curl -i -X POST http://localhost:8082/orders \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"origin_node_id":"manual-tester","order_id":"manual-worker-001","kind":"http_request","payload":{"method":"GET","url":"https://example.invalid/health","headers":{"Accept":"application/json"}}}'
```

Each accepted request returns HTTP `202`, its order ID, and
`"status":"pending"`. The payloads are descriptions only: no command is run
and no request is sent to `example.invalid`. Query each node again:

```bash
for PORT in 8081 8082 8083; do
  printf '\nOrders on localhost:%s\n' "$PORT"
  curl -i -H "Authorization: Bearer $TOKEN" \
    "http://localhost:$PORT/orders"
done
```

The manager's response contains `manual-manager-001`, worker 1's response
contains `manual-worker-001`, and worker 2's response has an empty `orders`
array. Each order includes its ID, origin, kind, payload, creation time, and
status. The endpoint returns only the responding node's queue, not a
network-wide view. Re-sending an ID to the same node returns HTTP `400`; IDs
are independent between nodes. An unsupported HTTP method such as `TRACE`
returns HTTP `400`, and an incorrect token returns HTTP `401`.

Pending orders remain listed until the next one-minute processing cycle. The
node logs each dry-run order to stdout, updates counters, marks it completed,
and then omits it from `GET /orders`. There is no HTTP processing trigger;
each running node processes its own queue automatically. If a cycle occurs
between submitting an order and querying the queue, the order may already be
completed and omitted from the response.

## Optional single-worker source check

These steps exercise the live HTTP receiver with `curl` and the local queue
processor. The processor has no HTTP endpoint, so the final check uses a small
Python snippet to inspect and drain an in-memory node. Orders are always
descriptive in this increment: neither commands nor HTTP requests are carried
out.

### Start a worker with an `.ini` token

From the repository root, install the Python requirements if they are not
already installed:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
```

Generate a strong random token using Python's standard library:

```bash
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Copy the printed value. Make a local copy of the worker configuration, then
add an `[auth]` section containing that value:

```bash
cp configs/node2.ini /tmp/project2-worker.ini
```

The end of `/tmp/project2-worker.ini` should contain:

```ini
[auth]
order_token = PASTE_THE_GENERATED_VALUE_HERE
```

Replace the example value with the generated token (without quotes). Do not
put a real secret in a tracked config file or commit this local config. Start
the worker with the source package and ensure the environment override is
unset so the `.ini` value is used:

```bash
unset ELVIS_ORDER_TOKEN
export PYTHONPATH="$PWD/src"
python3 -m elvis_botnet.main --config /tmp/project2-worker.ini
```

Leave this terminal running. In another terminal, set `TOKEN` to the exact
value entered in the `.ini` file and use port `8080`:

```bash
TOKEN='PASTE_THE_GENERATED_VALUE_HERE'
BASE_URL='http://localhost:8080'
```

The sample worker config uses the default port, `8080`. If that port is already
in use, add `port = 8084` under its `[node]` section and change `BASE_URL`
accordingly before starting the worker.

### Check the API and authentication

The health endpoint should respond with HTTP `200`:

```bash
curl -i "$BASE_URL/health"
```

With a configured token, a request with no bearer token or a wrong token should
respond with HTTP `401` and `{"error":"invalid order"}`. For example:

```bash
curl -i -X POST "$BASE_URL/orders" \
  -H 'Content-Type: application/json' \
  -d '{"origin_node_id":"manager-1","kind":"execute","payload":{"command":"echo"}}'

curl -i -X POST "$BASE_URL/orders" \
  -H 'Authorization: Bearer definitely-not-the-token' \
  -H 'Content-Type: application/json' \
  -d '{"origin_node_id":"manager-1","kind":"execute","payload":{"command":"echo"}}'
```

Both valid order kinds should return HTTP `202` with an order ID and
`"status":"pending"`. The first example lets the receiving node generate the
ID; the second supplies one explicitly:

```bash
curl -i -X POST "$BASE_URL/orders" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"origin_node_id":"manager-1","kind":"execute","payload":{"command":"echo","arguments":["hello"]}}'

curl -i -X POST "$BASE_URL/orders" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"origin_node_id":"manager-1","order_id":"manual-http-001","kind":"http_request","payload":{"method":"GET","url":"https://example.invalid/health","headers":{"Accept":"application/json"}}}'
```

The HTTP order above is only queued; the node does not contact
`example.invalid`. Re-send the second request unchanged to check duplicate-ID
rejection: it should return HTTP `400` with `{"error":"invalid order"}`.

This malformed order should also return HTTP `400` and should not be enqueued:

```bash
curl -i -X POST "$BASE_URL/orders" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"origin_node_id":"manager-1","kind":"http_request","payload":{"method":"TRACE","url":"https://example.invalid/health"}}'
```

To check the unconfigured-token case, stop the worker, remove or blank
`order_token` in the local config, ensure `ELVIS_ORDER_TOKEN` is unset, and
restart it. A `POST /orders` request then returns HTTP `503` with
`{"error":"order submission unavailable"}`. Restore the token and restart the
worker before continuing. The environment variable, when non-empty, takes
precedence over the `.ini` value.

### Check enqueueing, dry-run processing, and status counters

`GET /orders` inspects active orders, but there is no HTTP route to drain a
node's order queue.
Run the following from the repository root with the virtual environment
activated and `PYTHONPATH` set as above. It creates a separate in-memory worker
using the same local `.ini` file, sends both supported order kinds through its
Flask test client, and checks their pending-to-completed lifecycle:

```bash
python3 - <<'PY'
import configparser

from elvis_botnet.order import OrderStatus
from elvis_botnet.worker import Worker

config = configparser.ConfigParser()
if not config.read("/tmp/project2-worker.ini"):
    raise SystemExit("Could not read /tmp/project2-worker.ini")

node = Worker(config)
client = node.app.test_client()
headers = {"Authorization": f"Bearer {node.order_token}"}
orders = [
    {
        "origin_node_id": "manager-1",
        "kind": "execute",
        "payload": {"command": "echo", "arguments": ["dry run"]},
    },
    {
        "origin_node_id": "manager-1",
        "kind": "http_request",
        "payload": {
            "method": "GET",
            "url": "https://example.invalid/health",
        },
    },
]

accepted = []
for body in orders:
    response = client.post("/orders", json=body, headers=headers)
    assert response.status_code == 202, response.get_data(as_text=True)
    order_id = response.get_json()["order_id"]
    order = node.order_queue.get(order_id)
    assert order is not None and order.status is OrderStatus.PENDING
    accepted.append(order)

assert node.commands_received == 0
assert node.commands_completed == 0
assert node.process_pending_orders() == 2
assert all(order.status is OrderStatus.COMPLETED for order in accepted)
assert node.commands_received == 2
assert node.commands_completed == 2
assert node.process_pending_orders() == 0
print("PASS: two orders enqueued, dry-run completed, counters updated")
PY
```

The worker started for the `curl` checks is a different process, so its queue
is not the queue used by this in-memory lifecycle check. This is expected:
queues are in-memory and local to each process. `GET /orders` lists active
orders only; there is no per-order lookup for completed orders or remote
processing trigger.
