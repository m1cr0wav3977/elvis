# Project 2 Design

## Scope

Project 2 adds the first step in node-to-node communication: a node can accept
a structured order, authenticate the sender with a shared bearer token, and
place the order in its local queue. Nodes can explicitly drain that queue in
dry-run mode. This document describes the Project 2 changes only; the
Project 1 node hierarchy and status routes are documented separately in
[project1.md](./project1.md).

Order processing is intentionally non-operational at this stage. An
`execute` order is not run as a system command, and an `http_request` order is
not sent over the network. Processing logs what would have happened, then marks
the order complete. This provides an end-to-end data and queue lifecycle
without carrying out the requested work.

## Order model

Each order contains:

- `order_id`: unique order identifier; generated by the receiver when omitted
  from a request.
- `origin_node_id`: ID of the node that originated the order.
- `kind`: either `execute` or `http_request`.
- `payload`: a kind-specific object describing the work.
- `created_at`: UTC creation timestamp generated by the receiving node.
- `status`: local lifecycle state, initially `pending`.

For `execute`, `payload.command` is a non-empty command name and
`payload.arguments` is an optional list of strings. For `http_request`,
`payload.method` is one of `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, or
`OPTIONS`; `payload.url` must be an absolute HTTP(S) URL. Optional `headers`
are string-to-string pairs and an optional `body` can contain JSON data.
Unknown envelope and payload fields are rejected.

Example system-command description:

```json
{
  "origin_node_id": "manager-1",
  "kind": "execute",
  "payload": {
    "command": "echo",
    "arguments": ["hello"]
  }
}
```

Example HTTP-request description:

```json
{
  "origin_node_id": "manager-1",
  "kind": "http_request",
  "payload": {
    "method": "GET",
    "url": "https://example.invalid/health",
    "headers": {
      "Accept": "application/json"
    }
  }
}
```

In both cases these are data descriptions only: the current implementation
does not execute the command or send the HTTP request. The optional top-level
`order_id` may be included by the sender; `created_at` and `status` are
receiver-managed and are not accepted as request fields.

## Receiving orders and authentication

The base `Node` registers `POST /orders`, so both manager and worker nodes
currently expose the same receiver. Requests use the JSON envelope described
above and an `Authorization: Bearer <token>` header. The receiving node reads
the expected shared token from its configuration:

```ini
[auth]
order_token = <shared-secret>
```

An empty or missing configured token disables order submission. An invalid
token is rejected, and the token comparison uses Python's standard-library
`hmac.compare_digest`. After authentication, the route validates the envelope
and kind-specific payload, creates an `Order`, and enqueues it. A successful
request returns HTTP `202` with the order ID and `pending` status. Reusing an
order ID already known to that node is rejected.

The bearer token is a shared secret, not a distinct identity for each peer;
this version does not enforce manager-versus-worker permissions. The API uses
the project's existing Flask HTTP service and does not add an external
dependency. The token is not itself encrypted in transit: use only in the
isolated development setup until transport security is designed and deployed.

## Per-node queue and dry-run processing

Each node owns an `OrderQueue` with a FIFO collection of pending orders and a
lookup of orders already accepted by that node. Taking an order removes it
from the pending FIFO but retains its record for status inspection. Local
status transitions are:

```text
pending -> processing -> completed
```

`Node.process_pending_orders()` drains the queue when explicitly called. It
logs the order ID, kind, and origin, updates the existing received/completed
counters, and marks the order complete. The receive route does not invoke this
method. There is no background scheduler or central control loop yet.

## Not implemented in this increment

- A manager-facing human/CLI interface for authoring and issuing orders.
- Manager-to-worker forwarding, peer-manager coordination, or completion
  acknowledgements reported back to the originating manager.
- Role-based authorization or a per-peer authentication scheme.
- Actual system-command execution or outbound HTTP requests.
- Background processing or retry behavior.
- TLS or other transport encryption.

These items remain separate design and implementation work. In particular,
the shared bearer token does not protect traffic from interception, and the
dry-run processor must remain non-operational until execution and network
behavior are separately designed and authorized.
