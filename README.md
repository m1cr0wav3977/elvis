# elvis-botnet

## Overview

Elvis-Botnet is a for education only Peer-to-Peer botnet for a class for my masters degree, CS610 Networking and Security. This code will not have any malicious function. At project completion, it will have the ability for nodes to run and manage communications among one another in a peer to peer fashion. I have a strong interest in the actions of threat intelliegence groups and government agencies to take down malicious botnets. What better way to learn how they work than to build one?

The project will be submitted in 4 installments:

1. Project design and base classes. Establish what makes a "node" and differentiate between manager and worker nodes. Make and deploy a POC that shows the nodes run and respond to HTTP requests with basic information.

2. Node communication. Have nodes be able to receive and action orders. Need authentication mechanism.

3. Peer list structure and methods - how do you prevent each node from having a list of all other nodes? How do you keep track of how many nodes you have? Establish precedence between manager and worker nodes.

4. How can traffic between nodes be secured and/or obscured?

This project will not workaround NAT and will assume that all nodes are available publicly. The output is a Linux binary, no Windows compatibility. 


## Quick start

Requirements: Python 3.11 or newer, Docker, and Docker Compose.

Build the node and start the three-node Docker demo:

```bash
./run.sh
```

The demo uses one shared order token for all nodes. If `ELVIS_ORDER_TOKEN` is
unset or empty, `run.sh` generates a random token and prints it so you can use
it in local API tests. Treat this generated token as a local-testing
convenience, not a production secret. To use your own token for repeatable
testing, set the environment variable before launching:

```bash
export ELVIS_ORDER_TOKEN='your-lab-shared-secret'
./run.sh
```

For a standalone node, the same secret can be set as `order_token` in that
node's `[auth]` config section instead. When both are set, a non-empty
`ELVIS_ORDER_TOKEN` takes precedence. Keep real secrets out of committed config
files and source control.

Build and run only the standalone binary:

```bash
./scripts/build.sh
./build/elvis-node
```

### API usage

The application listens on port `8080` inside each container. The Docker demo
publishes the manager at host port `8081` and its two workers at host ports
`8082` and `8083`. Every node exposes `GET /health` and `GET /info`. Manager
and worker nodes also expose `GET /status`, which adds their peer tables to the
base node info. Nodes accept `POST /orders`; each receiving node must have an
`[auth] order_token` configured or `ELVIS_ORDER_TOKEN` set in its environment.
Both `GET /orders` and `POST /orders` require the shared bearer token. The
POST endpoint validates and enqueues an order; each node automatically drains
its local queue every 60 seconds in dry-run mode through
`Node.process_pending_orders()`.

```bash
# Base info shared by all nodes
curl http://localhost:8081/health
curl http://localhost:8081/info

# Manager node: node info + known peer managers + overseen workers
curl http://localhost:8081/status

# Worker node: node info + overseeing manager's IP
curl http://localhost:8082/status

# Active local orders (requires the configured bearer token)
curl -H "Authorization: Bearer $ELVIS_ORDER_TOKEN" http://localhost:8082/orders

# Submit a sample order once [auth] order_token is configured on the worker
curl -X POST http://localhost:8082/orders \
  -H "Authorization: Bearer YOUR_SHARED_ORDER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"origin_node_id":"manager-1","kind":"execute","payload":{"command":"echo","arguments":["hello"]}}'
```

`GET /orders` is available on managers and workers. It requires the same
bearer token as `POST /orders` and returns that node's pending and processing
orders; completed orders are omitted.

#### `POST /orders` JSON structure

Every request uses this top-level shape. `origin_node_id`, `kind`, and
`payload` are required. `order_id` is optional and is generated by the
receiving node if omitted. The receiver sets the order's creation time and
status; clients must not send those fields. Include the configured bearer token
in the `Authorization` header.

```json
{
  "origin_node_id": "manager-1",
  "kind": "execute",
  "payload": {
    "command": "echo",
    "arguments": ["hello"]
  }
}
```

For `kind: "execute"`, `payload.command` is a non-empty command name and
`payload.arguments` is an optional list of strings. These fields describe a
system command only; the current implementation does not execute it.

For `kind: "http_request"`, provide an HTTP method and absolute HTTP(S) URL.
`method` must be one of `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, or
`OPTIONS`. Headers and JSON body are optional:

```json
{
  "origin_node_id": "manager-1",
  "kind": "http_request",
  "payload": {
    "method": "GET",
    "url": "https://example.invalid/health",
    "headers": {
      "Accept": "application/json"
    }
  }
}
```

The current implementation does not send this request. A successful enqueue
returns HTTP `202` with the generated or supplied order ID and `"status":
"pending"`.

To smoke-test the API on all three Compose nodes, start the demo with a shared
token in the environment:

```bash
export ELVIS_ORDER_TOKEN='the-same-secret-configured-for-node1'
./run.sh
```

In another terminal, export the same token and run:

```bash
export ELVIS_ORDER_TOKEN='the-same-secret-configured-for-node1'
bash scripts/test.sh
unset ELVIS_ORDER_TOKEN
```

The script displays each request and its response body, HTTP status, and curl
exit status. It submits a uniquely identified order to each node and then
requests each node's active queue; it does not assert response contents or
explicitly trigger processing. A scheduled processing cycle may run while the
script is executing. It requires `curl` and Bash. Set
`ELVIS_MANAGER_URL`, `ELVIS_WORKER1_URL`, or `ELVIS_WORKER2_URL` to override
the corresponding localhost URL. Do not commit the secret in a config file or
source code. The demo configuration files are copied into the container image
during build; rebuild the image after editing them.
